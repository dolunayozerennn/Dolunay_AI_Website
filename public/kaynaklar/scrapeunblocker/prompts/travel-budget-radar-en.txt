Build this product from scratch. Run every command, file creation and test yourself; ask for no
terminal work and clone no repository. Build it in a clean `travel-budget-radar` folder.

## Outcome

Create a local product that answers this question without requiring a destination: "Given my
departure point, dates, and per-person budget, where can I travel?"

Make a decision screen, not a flight dump. First show in-budget routes, per-person price, dates,
stops, duration, airline, baggage, and source link. Missing baggage is `unknown`.

All network data must come through ScrapeUnblocker. Do not use another data API. Never invent a fare when data is missing.

## Installation

Verify Python 3.11 or newer. Create `.venv` inside the project. Put exactly
`scrapeunblocker==0.1.8` in `requirements.txt` and install that official SDK version in the
virtual environment; fail with a clear message if the runtime version is not 0.1.8. Add `.env`,
`.venv/`, cache, raw responses, run state and capability evidence to `.gitignore`.

Never request the API key in chat. If `SCRAPEUNBLOCKER_KEY` is absent from the environment,
collect it with Python `getpass` as hidden terminal input. `getpass` runs only in the
argument-free interactive run: `--help`, `--fixture-demo`, and `--plan` are non-interactive and
read the key only from the environment or `.env`; when it is missing, exit non-zero with a clear
message and never reach `getpass`. Save it to the project's `.env` with
`0600` permissions. The key must never appear in HTML, JSON, logs, command-line arguments, fixtures,
or terminal output.

## User input

Collect these product-level answers once: departure city or airport, one or two outbound/return
date windows, trip length, per-person budget and currency, maximum stops, longest acceptable one-way time, places that must be allowed, places that must be excluded, and Quick or
Deep mode.

Ask no technical field names. Turn the answers into `plan.json` yourself. The departure record
and every candidate need a name, plain search name, and one or more IATA codes. Create candidates
from general knowledge, without API calls. Apply allow and exclude lists exactly.

## Canonical CLI contract

The only root entry point is `app.py`; create no alternative. Its exact interface is:

- `python app.py --help` -> usage and `exit 0`.
- `python app.py --fixture-demo` -> keyless local demo.
- `python app.py --plan PLAN_JSON` -> non-interactive live flight run.
- `python app.py --plan PLAN_JSON --hotel-canary` -> explicit hotel canary.
- Argument-free `python app.py` -> the only interactive mode; collect answers once and run.

`--fixture-demo` and `--plan` are exclusive; `--hotel-canary` requires `--plan`. Invalid combinations
exit `2` without input. `--help` exits `0` without stdin/`input`, `getpass`, SDK/network, or any file
write. Do not import the SDK at module level; import `scrapeunblocker` lazily inside the
function that makes the live call.

## Two exact modes

| Mode | Destinations | Date windows | Successful flight responses | Network attempts (incl. retries) |
|---|---:|---:|---:|---:|
| Quick (default) | 8 | 1 | 8 | 24 |
| Deep | 20 | 2 | 40 | 120 |

Enforce these ceilings in code; a larger `plan.json` value must not override them. Run requests sequentially, concurrency 1.

## ScrapeUnblocker integration

Open the official SDK with `Client(..., max_retries=0)`; the app owns the retry policy.
Use `client.skyscanner.flights(...)` for flights. Supply:

- `origin`, `dest`, `depart_date`, `return_date`,
- `adults`, `cabin`, `market`, `locale`, `currency`, `max_polls`.

Never invent the response shape. A live measurement on 14 August 2026 returned these field
paths; read the names verbatim: root `itineraries`, result list `itineraries.results`, status
`itineraries.context.status`. Each result carries `legs` (outbound `legs[0]`, return `legs[1]`
when present), `legs[].origin.id` and `legs[].destination.id` (IATA), `legs[].departure` /
`legs[].arrival`, `legs[].durationInMinutes` (one-way minutes), `legs[].stopCount`,
`legs[].carriers.marketing[].name`, `price.raw` (number), `price.formatted` (string), and the
booking link `pricingOptions[0].items[0].url` (prefix a relative path with
`https://www.skyscanner.net`). Invent no other field; a result with an empty price is not a
price result.

For every route and window, use the planned IATA code in the first request for both `origin` and
`dest`. Validate the first leg's airports against the expected IATA sets; a response resolved to
a different city is not a price result.

Plain-city fallback is a run-wide state machine, never Cartesian. Start
`origin_city_fallback_attempts` and `dest_city_fallback_attempts` at `0`; neither may exceed `1`.

- Normal: `origin_IATA/dest_IATA`.
- Destination alone wrong and its counter `0`: once `origin_IATA/dest_plain_city`.
- Origin alone wrong and its counter `0`: once `origin_plain_city/dest_IATA`.
- For `404`, empty, or ambiguous output, try the unused destination fallback, then origin fallback.
- Forbid `origin_plain_city/dest_plain_city`, nested candidate loops, identical retries, and any
  later city fallback on a spent side.

A `2 destinations x 2 windows` fixture test must prove the exact
SDK call order for an ambiguous failure: first route `IATA/IATA`, `IATA/dest_plain_city`,
`origin_plain_city/dest_IATA`; all remaining calls only `IATA/IATA`. Assert both counters stay `<=1`.

Code must contain one named decision gate, the `FALLBACK_TRIGGER_MATRIX` constant. `ALLOW`: only
`not_found_404`, usable `2xx_empty`, `origin_wrong`, `dest_wrong`, `route_ambiguous`. `DENY`:
`400/401/402/403/422`, `429/500/502/503/504/timeout_exhausted`, `200_block_page`, `unknown_error`.

Only an `ALLOW` result may enter scanner fallback; a generic exception/failure path may not. In a
table test named `test_fallback_trigger_matrix_at_scanner_boundary`, drive the fake SDK through
the real route-scanner boundary: every `DENY` row logs exactly one `IATA/IATA` call, keeps both
counters at `0`, and contains no city query; `not_found_404` proves the allowed exact sequence
above. Testing only the gateway/HTTP classifier is insufficient.

Before the full scan, run one startup canary using the first route and first window. If the canary
errors, resolves to the wrong city, returns nothing, or has no option inside the stop and duration
limits, do not begin the scan. Produce a dark `rapor_son.html` that says `Scan not started`, shows
the actual reason, and contains no sample fare.

## Error and retry contract

- `400`, `401`, `402`, `422`: key, plan, or parameter error. Do not retry; stop immediately.
- `403`: source block. Do not repeat the same request.
- `404`: endpoint or result unavailable. Do not repeat the same request. Only the run-wide,
  one-per-side plain-city state machine above may run.
- `429`, network timeout, `500`, `502`, `503`, `504`: three attempts in total; wait one second
  after the first failure and two after the second.
- An HTTP `200` body with a captcha, access-denied page, or human verification is not success.
- For an unknown failure, never synthesize data; show the row incomplete with its reason.

Count only usable `2xx` responses as successful and billable. Track attempts, successful 2xx and cache hits
separately. Never estimate remaining credits.

## Fare safety

`adults` group totals are unverified: label fares `per person`; for two+ travelers never multiply
and say `Group total not verified`. Never infer missing baggage. Compare budget only in the requested
currency; never convert or count other currencies as in-budget, and warn. State fares can change.

## Cache, history, and incremental output

Cache every successful route response as gzipped JSON, keyed by SHA-256 of the endpoint and
parameters and never containing the API key. TTL is six hours. A cache hit must not increase the
network-attempt or 2xx counters.

After every completed search, immediately rewrite `rapor_son.html` and `run_manifest.json` so
the user can see the first opportunities while a long scan continues. The manifest must carry at
least: prompt and SDK versions; run ID plus UTC start and finish times; mode and hard budgets;
status (starting, canary, running, completed, partial, blocked); completed and planned searches;
network attempts, successful 2xx responses and cache hits; `origin_city_fallback_attempts` and
`dest_city_fallback_attempts`; data sources, warnings and output path.

Keep price history in a separate JSON file. Compare only runs with the same origin, windows, trip
length, currency, stop limit, and duration limit. Mark routes as new, down, up, or unchanged.
Never headline a sub-one-percent change as a major alert. Keep timestamps for seven runs.

## Hotel capability gate

Hotels are off by default. Only explicit `--hotel-canary` may call
`client.skyscanner.hotels(...)`. Record a run ID only for a real name, numeric total, and
currency. Do not promise/search hotels before two distinct live run proofs; afterward require
explicit choice and at most three in-budget routes. Never add different currencies, and never
show a combined trip total, because flight group totals are unverified.
