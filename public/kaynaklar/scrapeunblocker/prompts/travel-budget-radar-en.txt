## Outcome

Create a local product that answers this question without requiring a destination:

"Given my departure point, dates, and per-person budget, where can I travel?"

Make a decision screen, not a flight dump. First show in-budget routes, per-person price, dates,
stops, duration, airline, baggage, and source link. Missing baggage is `unknown`. Compare later
runs with timestamped history.

All network data must come through ScrapeUnblocker. Do not use another data API. Never invent a
fare when data is unavailable.

## Canonical CLI contract

The only root entry point is `app.py`; create no alternative. Its exact interface is:

- `python app.py --help` -> usage and `exit 0`.
- `python app.py --fixture-demo` -> keyless local demo.
- `python app.py --plan PLAN_JSON` -> non-interactive live flight run.
- `python app.py --plan PLAN_JSON --hotel-canary` -> explicit hotel canary.
- Argument-free `python app.py` -> the only interactive mode; collect answers once and run.

`--fixture-demo` and `--plan` are exclusive; `--hotel-canary` requires `--plan`. Invalid combinations
exit `2` without input. `--help` exits `0` without stdin/`input`, `getpass`, SDK/network, or any file

## Two exact modes

`Quick` is the default:

- at most 8 destinations,
- exactly 1 date window,
- at most 8 successful flight responses,
- at most 24 network attempts including retries.

`Deep`:

- at most 20 destinations,
- at most 2 date windows,
- at most 40 successful flight responses,
- at most 120 network attempts including retries.

Enforce these ceilings in code. A larger value in `plan.json` must not override them. Run requests
sequentially, with concurrency fixed to 1.

## ScrapeUnblocker integration

Open the official SDK with `Client(..., max_retries=0)` so the application owns the retry policy.
Use `client.skyscanner.flights(...)` for flights. Supply:

- `origin`, `dest`, `depart_date`, `return_date`,
- `adults`, `cabin`, `market`, `locale`, `currency`, `max_polls`.

For every route and window, use the planned IATA code in the first request for both `origin` and
`dest`. Validate the first-leg origin and destination airports against the expected IATA sets. A
response resolved to a different city must never become a price result.

Plain-city fallback is a run-wide state machine, never Cartesian. Start
`origin_city_fallback_attempts` and `dest_city_fallback_attempts` at `0`; neither may exceed `1`.

- Normal: `origin_IATA/dest_IATA`.
- Destination alone wrong and its counter `0`: once `origin_IATA/dest_plain_city`.
- Origin alone wrong and its counter `0`: once `origin_plain_city/dest_IATA`.
- For `404`, empty, or ambiguous output, try the unused destination fallback, then origin fallback.
- Forbid `origin_plain_city/dest_plain_city`, nested candidate loops, identical retries, and any
  later city fallback on a side whose counter was consumed.

Put both counters in the manifest. A `2 destinations x 2 windows` fixture test must prove the exact
SDK call order for an ambiguous failure: first route `IATA/IATA`, `IATA/dest_plain_city`,
`origin_plain_city/dest_IATA`; all remaining calls only `IATA/IATA`. Assert both counters stay `<=1`.

Code must contain one named decision gate, the `FALLBACK_TRIGGER_MATRIX` constant:

- `ALLOW`: only `not_found_404`, usable `2xx_empty`, `origin_wrong`, `dest_wrong`, and
  `route_ambiguous`.
- `DENY`: `400/401/402/403/422`, `429/500/502/503/504/timeout_exhausted`, `200_block_page`, and
  `unknown_error`.

Only an `ALLOW` result may enter scanner fallback; a generic exception/failure path may not. Add a
table test named `test_fallback_trigger_matrix_at_scanner_boundary` that drives the fake SDK through
the real route-scanner boundary. Every `DENY` row must log exactly one `IATA/IATA` call, keep both
fallback counters at `0`, and contain no city query. `not_found_404` must prove the allowed exact
sequence above. Testing only the gateway/HTTP classifier is insufficient.

Before the full scan, run one startup canary using the first route and first window. If the canary
returns an API error, resolves to the wrong city, returns no result, or has no option matching the
user's stop and duration limits, do not begin the scan. Produce a dark `rapor_son.html` that
says `Scan not started`, shows the actual reason, and contains no sample fare.

## Error and retry contract

- `401` and `402`: authentication, plan, or quota problem. Stop immediately.
- `400` and `422`: invalid parameters. Do not retry; stop immediately.
- `403`: source block. Do not repeat the same request.
- `404`: endpoint or result unavailable. Do not repeat the same request. Only the run-wide,
  one-per-side plain-city state machine above may run.
- `429`, network timeout, `500`, `502`, `503`, and `504`: allow three attempts in total. Wait one
  second after the first failure and two seconds after the second.
- If an HTTP `200` body contains a captcha, access-denied page, or human verification, do not count
  it as success.
- For an unknown failure, preserve the reason and mark the row incomplete. Never synthesize data.

Count only usable `2xx` responses as successful and billable. Track network attempts, successful
2xx responses, and cache hits separately. Never estimate the account's remaining credits.

## Fare safety

`adults` group totals are unverified: label fares `per person`; for two+ travelers never multiply
and say `Group total not verified`. Never infer missing baggage. Compare budget only in the requested
currency; do not convert or count other currencies as in-budget, and warn. State fares can change.

## Cache, history, and incremental output

Cache every successful route response as gzipped JSON. Build the cache key with SHA-256 from the
endpoint and parameters, never from the API key. Use a six-hour TTL. A cache hit must not increase
the network-attempt or successful-2xx counters.

After every completed search, immediately rewrite `rapor_son.html` and `run_manifest.json` so
the user can see the first opportunities while a long scan continues. The manifest must contain:

- prompt and SDK versions,
- run ID plus UTC start and finish times,
- mode and hard budgets,
- status: starting, canary, running, completed, partial, or blocked,
- completed and planned searches,
- network attempts, successful 2xx responses, and cache hits,
- `origin_city_fallback_attempts` and `dest_city_fallback_attempts`,
- data sources, warnings, and output path.

Keep price history in a separate JSON file. Compare only runs with the same origin, windows, trip
length, currency, stop limit, and duration limit. Mark routes as new, down, up, or unchanged. Do
not feature changes below one percent as a major alert. Retain timestamps for at least seven runs.
